# docx-generation Specification

## Purpose

The MCP server's ability to convert Markdown or HTML text into a
well-formatted, consistently styled Word document (DOCX) and return it as a
structured MCP content response - suitable for remote operation without a
shared filesystem.

## Requirements

### Requirement: Conversion of Markdown to DOCX

The `convert_to_docx` tool of the `docx` toolset MUST convert Markdown text
passed via the `content` parameter with `format` set to `"markdown"` into a
valid DOCX document and return it as a structured MCP content response. The
conversion MUST preserve the document structure: headings by level, paragraphs,
bold and italic inline formatting, links, bullet and ordered lists (including
nesting), and tables with a styled header row.

#### Scenario: Markdown with common elements is converted

- **WHEN** `convert_to_docx` is called with `format` `"markdown"` and a Markdown
  document containing a top-level heading, a paragraph with bold and italic
  spans, a nested bullet list, an ordered list, and a pipe table
- **THEN** the tool returns a valid DOCX file result, and the document contains
  the heading as a Word heading style, the list items as Word list paragraphs
  with conventional indents, and the table with a styled header row

#### Scenario: Extended Markdown elements are converted

- **WHEN** `convert_to_docx` is called with `format` `"markdown"` and a Markdown
  document containing a strikethrough span, a task list, and a code block
- **THEN** the tool returns a valid DOCX file result, and the document contains
  the strikethrough formatting, the task list markers, and the code block

### Requirement: Conversion of HTML to DOCX

The `convert_to_docx` tool MUST convert HTML text passed via the `content`
parameter with `format` set to `"html"` into a valid DOCX document and return
it as a structured MCP content response, preserving the same structure classes
as Markdown input: headings, paragraphs, inline formatting, lists, and tables.

#### Scenario: HTML with common elements is converted

- **WHEN** `convert_to_docx` is called with `format` `"html"` and an HTML
  document containing `<h1>`-`<h3>` headings, a paragraph with `<strong>` and
  `<em>` spans, a `<ul>` and an `<ol>`, and a `<table>`
- **THEN** the tool returns a valid DOCX file result, and the document contains
  the headings as Word heading styles, the lists as Word list paragraphs, and
  the table with a styled header row

### Requirement: Standardized document styling

Every document generated by `convert_to_docx` MUST use one fixed, shipped set
of Word styles - the same heading styles, body font, and table look for every
call - independent of the input format, so all generated documents share a
clean, standardized visualization.

#### Scenario: Styling is identical across formats

- **WHEN** `convert_to_docx` is called twice with the same content expressed
  once as Markdown and once as HTML
- **THEN** both returned documents use the same named heading styles, body font,
  and table style

#### Scenario: Table styling is applied

- **WHEN** the input contains a table
- **THEN** the generated document renders the table with a shaded header row
  and visible cell borders

### Requirement: Image handling

`convert_to_docx` MUST embed images passed as base64 data URIs in the input
into the generated document and MUST fetch remote http(s) image URLs during
conversion.

#### Scenario: Data-URI image is embedded

- **WHEN** the input contains an image reference whose source is a base64 data
  URI
- **THEN** the generated document contains the embedded image

#### Scenario: Remote image is fetched and embedded

- **WHEN** the input contains an image reference to a reachable http(s) URL
- **THEN** the generated document contains the fetched image

#### Scenario: Unfetchable remote image degrades gracefully

- **WHEN** the input contains an image reference to an unreachable http(s) URL
- **THEN** the tool still returns a valid DOCX file result, in which the image
  is replaced by its description (pandoc warns and continues)

### Requirement: Document title metadata

`convert_to_docx` MUST accept an optional `title` parameter and, when provided,
set it as the Word document's core title property.

#### Scenario: Title is set

- **WHEN** `convert_to_docx` is called with `title` set to a non-empty string
- **THEN** the returned document's core title property equals that string

#### Scenario: Omitted title leaves a usable default

- **WHEN** `convert_to_docx` is called without `title`
- **THEN** the tool still returns a valid DOCX file result

### Requirement: Error handling for invalid input

The `convert_to_docx` tool MUST respond to invalid inputs with meaningful
errors, without crashing the server.

#### Scenario: Empty content

- **WHEN** `convert_to_docx` is called with `content` that is empty or only
  whitespace
- **THEN** the tool returns an error stating that the content must not be empty

#### Scenario: Unsupported format

- **WHEN** `convert_to_docx` is called with a `format` other than `"markdown"`
  or `"html"`
- **THEN** the tool returns an error that names the unsupported format and the
  supported values

#### Scenario: Converter unavailable

- **WHEN** the conversion engine binary is not available on the server
- **THEN** the tool returns an error that names the missing dependency

#### Scenario: Conversion failure

- **WHEN** a conversion run fails (for example a conversion-internal error or
  a timeout), so the conversion engine aborts with a non-zero exit
- **THEN** the tool returns a meaningful error, without the server crashing

### Requirement: Temporary file handling

`convert_to_docx` MUST process intermediate files only temporarily and leave no
files permanently behind on the server after the conversion.

#### Scenario: No file residue

- **WHEN** `convert_to_docx` has completed (successfully or with an error)
- **THEN** no temporary input or output file of the call exists any longer in
  the server's working directory
